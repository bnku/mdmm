# Задача 05. Цветной output, help и user-facing документация

**Статус:** ⏳ Запланировано

## Цель

Сделать CLI визуально и ментально понятным: успешные действия должны отличаться от ошибок с первого взгляда, а README и `--help` должны объяснять реальные сценарии использования вместо внутренней кухни репозитория.

Эта задача нужна для того, чтобы пользователь понимал не только синтаксис include, но и практический workflow работы с инструментом каждый день.

## Источники требований

- `../00-roadmap.md`
- `../../README.md`
- `../../src/cli.js`
- `../../package.json`
- Пользовательский запрос в текущей DX-сессии: не хватает цветового различия сообщений и неочевидно, как пользоваться пакетом в будущем.

## Что входит в задачу

- Ввести единый logger для success, warning, info и error-сообщений.
- Добавить цветной output с безопасным отключением.
- Переписать help вокруг коротких user workflows.
- Переписать README вокруг install/run сценариев, а не только вокруг внутренней структуры репозитория.
- Отделить user-facing usage от maintainer/development scripts.

## Что НЕ делаем в этой задаче

- Не добавляем TUI-интерфейс, progress bars или спиннеры.
- Не локализуем CLI на несколько языков.
- Не стабилизируем текст каждой ошибки как внешний API посимвольно; стабильными должны быть смысл и основные статусы, а не буквальный snapshot всех фраз.

## Основные задачи по слоям

### Feature

- Выделить общий logger/formatter слой для stdout/stderr.
- Подсветить `OK`, `Built`, `Wrote`, warning и error-сообщения разными цветами.
- Поддержать минимум `NO_COLOR` и `--no-color`.
- Переписать `mdmm --help` так, чтобы он содержал install/use examples: `npx`, global install и локальная установка как devDependency.
- Добавить в help короткие next steps после `init` и для уже существующего проекта.

### Backend

- Отдельный backend не требуется.
- Если CLI запускается в non-TTY или в CI, formatter должен корректно переходить в plain text mode.

### Frontend

- UI продукта не затрагивается.
- CLI вывод остается совместимым с обычным терминалом и CI-логами.

### Contracts/API

- Зафиксировать, что цвет по умолчанию включается только там, где это уместно, и может быть отключен через `NO_COLOR` или `--no-color`.
- Зафиксировать пользовательские сценарии в help/README:
  - `npx mdmm@latest init`
  - `npx mdmm@latest build`
  - `npm i -g mdmm` -> `mdmm ...`
  - `npm i -D mdmm` + npm script для командной работы в проекте
- Зафиксировать разделение документации на `User Usage` и `Development`.

### Tests

- Добавить тесты на formatter/logger без TTY: plain text без ANSI-последовательностей.
- Добавить тест на `--no-color`.
- Добавить тесты, что help содержит install/run сценарии, а не только список команд.
- Добавить тесты на основные success/error summary lines после `check`, `build` и `report`.

### Docs

- Переписать README в структуре: что это такое, как установить, как начать, как использовать, как развивать сам репозиторий.
- Добавить отдельный раздел с рекомендованным способом командной установки: `npm i -D mdmm` и scripts в `package.json` документационного проекта.
- Явно отметить, какие команды и скрипты предназначены только для разработки самого `mdmm` (`smoke:bin`, `validate:examples`, `pack:dry-run`).

## Критерии готовности

- Успешный build и ошибка сборки визуально различимы без вчитывания в длинный текст.
- `mdmm --help` отвечает на вопрос «как мне начать?» для пустого проекта и для уже установленного пакета.
- README объясняет как минимум три пользовательских режима запуска: `npx`, global install и devDependency в проекте.
- В пользовательской документации нет смешения с внутренними maintainer-сценариями репозитория.
