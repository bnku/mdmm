# Задача 02. Include фрагментов внутри Mermaid

**Статус:** ✅ Реализован прототип

## Цель

Добавить второй уровень переиспользования: возможность собирать одну большую Mermaid-диаграмму из канонических фрагментов без ручной склейки кода и без конфликтов идентификаторов узлов.

Задача нужна только как продолжение первого этапа и должна запускаться после того, как include целых диаграмм подтвердит свою пользу и станет стабильной частью документационного пайплайна.

## Источники требований

- `../00-roadmap.md`
- `../../01-intro-and-architecture.md`
- Результаты первого этапа: согласованный синтаксис блоков, правила сборки и базовые CI-проверки.

## Что входит в задачу

- Определить синтаксис fragment-блока на базе обычного ` ```mermaid ` для переиспользуемых внутренних частей диаграммы.
- Определить синтаксис include внутри ` ```mermaid ` через Mermaid-комментарий.
- Реализовать alias/prefix rewriting для node id.
- Ввести явный контракт `exports` для узлов, доступных внешней диаграмме.
- Добавить расширенную валидацию конфликтов, ссылок и результатов раскрытия include.
- Подготовить авторскую документацию с примерами композиции диаграмм.

## Что НЕ делаем в этой задаче

- Не расширяем решение до произвольного DSL поверх Mermaid.
- Не вводим динамическую композицию по условиям окружения или ролям доступа.
- Не поддерживаем глубокую рекурсивную вложенность include без явной дополнительной необходимости.
- Не добавляем редакторские визуальные инструменты поверх Markdown.
- Не убираем и не заменяем механизм include целых диаграмм; он остается базовым сценарием по умолчанию.

## Основные задачи по слоям

### Feature

- Зафиксировать формат объявления фрагмента, например `<!-- mermaid:block <block-id> type=fragment exports=... -->`.
- Зафиксировать формат вставки во внутренность диаграммы, например `%% include: <path>#<block-id> as <alias>`.
- Реализовать переписывание node id по префиксу `<alias>__`.
- Обеспечить предсказуемую подстановку фрагмента в итоговый ` ```mermaid ` блок.
- Определить ограничения на вложенность, область видимости alias и правила именования exports.

### Backend

- Отдельный backend не требуется.
- Если документационный pipeline исполняется на серверной стороне, расширить сборочный шаг так, чтобы fragment include проходил тем же маршрутом, что и v1 include.

### Frontend

- UI продукта не затрагивается.
- Если docs frontend поддерживает локальный preview исходников, проверить, как авторы будут видеть ошибки fragment include до CI, и при необходимости добавить локальный preview script.

### Contracts/API

- Описать формальный контракт фрагмента: что такое `exports`, когда alias обязателен, какие идентификаторы считаются публичными.
- Описать ошибки: missing alias, missing export, duplicate rewritten id, invalid fragment content, unresolved fragment include.
- Зафиксировать порядок применения правил: сначала разрешение блока, затем rewriting, затем итоговая Mermaid-валидация.

### Tests

- Покрыть позитивные кейсы: один фрагмент, несколько фрагментов, повторное использование одного и того же фрагмента с разными alias.
- Покрыть негативные кейсы: отсутствие alias, отсутствие export, конфликт rewritten id, циклический include, попытка ссылаться на несуществующий exported узел.
- Добавить smoke-тесты на итоговые сложные диаграммы после раскрытия нескольких fragment include.
- Проверить, что итоговый Mermaid-код остается валидным после rewriting и сборки.

### Docs

- Описать, когда автор должен использовать include целой диаграммы, а когда fragment include.
- Добавить примеры композиции и антипримеры, где fragment include избыточен.
- Зафиксировать правило: fragment include нужен только для больших обзорных диаграмм, а не для любого маленького фрагмента ради красоты.
- Описать ограничения второй версии и требования к отладке ошибок.

## Критерии готовности

- Один и тот же Mermaid-фрагмент может быть повторно использован внутри нескольких больших диаграмм без ручного переименования узлов.
- Внешняя диаграмма может ссылаться только на явно экспортированные точки входа и выхода фрагмента.
- Конфликты идентификаторов и ошибочные связи отлавливаются на сборке.
- Итоговый ` ```mermaid ` код после раскрытия fragment include проходит валидацию.
- Для авторов документации есть понятное правило выбора между целой диаграммой и fragment include.

## Что реализовано сейчас

- Поддержан тип блока `type=fragment` с fenced-содержимым ` ```mermaid `; при include первая строка с типом диаграммы удаляется.
- Поддержана inline-директива `%% include: <path>#<block-id> as <alias>` внутри ` ```mermaid `.
- Реализована префиксация идентификаторов узлов в формате `<alias>__<node-id>`.
- Реализована базовая проверка `exports`: внешняя диаграмма может ссылаться только на явно экспортированные узлы.
- Добавлены ошибки `MISSING_ALIAS`, `INVALID_BLOCK_TYPE`, `DUPLICATE_ALIAS`, `MISSING_EXPORT`, `UNRESOLVED_FRAGMENT_INCLUDE`.
- Добавлены примеры в `../../examples/docs/fragment-include.md` и `../../examples/shared/customer-verification.md`.
- Добавлены unit-тесты на позитивные и негативные сценарии во `../../test/preprocess.test.js`.
- Добавлена end-to-end Mermaid-валидация собранного примера через `../../scripts/validate-mermaid-cli.js`.
