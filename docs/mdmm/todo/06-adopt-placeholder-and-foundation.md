# Задача 06. Placeholder для `adopt` и foundation для future retrofit

**Статус:** ⏳ Запланировано

## Цель

Подготовить безопасный маршрут для будущего внедрения `mdmm` в уже существующие docs-проекты, где диаграммы уже размазаны по десяткам Markdown-файлов и часть из них потенциально дублируется.

Задача нужна не для полной реализации мигратора сейчас, а для того, чтобы текущий DX не блокировал этот сценарий и не вынуждал позже ломать уже опубликованный CLI surface.

## Источники требований

- `../00-roadmap.md`
- `../../src/report.js`
- `../../src/blocks.js`
- `../../src/references.js`
- Пользовательский запрос в текущей DX-сессии: в будущем нужен скрипт, который поможет внедрить `mdmm` в существующий docs-проект, вытащит общие диаграммы в `shared` и подготовит single source of truth.

## Что входит в задачу

- Зафиксировать `adopt` как отдельный сценарий рядом с `init`, а не как режим внутри `init`.
- Описать безопасную первую версию `adopt`: analyze-first, без автоматической перезаписи Markdown.
- Подготовить foundation-слой, который потом можно использовать для inventory и duplicate analysis.
- Согласовать, какие уже существующие модули (`blocks`, `references`, `report`) будут опорой для будущего `adopt`, а какие стоит отделить в более общий analysis layer.

## Что НЕ делаем в этой задаче

- Не делаем автоматический перенос диаграмм в `shared/`.
- Не реализуем эвристики дедупликации Mermaid на уровне production-кода.
- Не переписываем существующие `.md`-файлы.
- Не обещаем точную будущую форму refactoring patches до отдельной planning/implementation сессии.

## Основные задачи по слоям

### Feature

- Добавить placeholder-команду `mdmm adopt`, которая описывает будущую зону ответственности команды.
- Зафиксировать базовый будущий pipeline `adopt`: scan -> inventory -> duplicate candidates -> migration suggestions -> explicit write/apply step в отдельной очереди.
- Определить минимальные reusable primitives для будущего анализа: перечисление Mermaid-блоков, нормализованное описание источников, usage/dependency inventory.
- Избежать жесткой привязки `init`-логики к greenfield-only предположениям, которые потом будут мешать `adopt`.

### Backend

- Отдельный backend не требуется.
- Если в будущем `adopt` будет интегрироваться в CI как read-only audit, foundation должен уметь работать без интерактивного режима и без записи на диск.

### Frontend

- UI продукта не затрагивается.
- Любой будущий interactive review UI откладывается; текущая foundation остается CLI-first.

### Contracts/API

- Зафиксировать, что `adopt` в первой будущей версии - read-only analysis command.
- Зафиксировать принцип безопасности: запись или rewrite существующих документов возможны только через отдельный явный opt-in режим в будущей очереди (`--write`, `--apply` или аналог), но не по умолчанию.
- Зафиксировать, что текущее наличие `report` и analysis primitives не гарантирует еще стабильный JSON/API контракт для `adopt`; он будет определен отдельной задачей, когда появится реальная реализация.

### Tests

- Добавить smoke-тест на placeholder `adopt`.
- Если в рамках foundation будут выноситься reusable analysis helpers, покрыть их тестами отдельно от `cli.js`.
- Добавить regression-тест, что `init` и обычные `build/check/report` сценарии не начинают зависеть от незавершенной логики `adopt`.

### Docs

- Добавить в README и help короткое объяснение: `init` для нового проекта, `adopt` для будущего внедрения в существующий.
- Зафиксировать, что текущий roadmap не обещает автоперенос diagram library в этой очереди, а лишь сохраняет для него место в публичном surface.
- При появлении реальной реализации `adopt` подготовить отдельный feature-folder или самостоятельный task-пакет, если объем миграционной логики станет существенно больше текущего DX-этапа.

## Критерии готовности

- CLI surface уже сейчас учитывает существование отдельного retrofit-сценария и не смешивает его с `init`.
- Пользователь не получает ложного впечатления, что `adopt` уже умеет безопасно переписывать документацию.
- Текущие DX-решения не блокируют будущую реализацию inventory/deduplication/migration flow.
