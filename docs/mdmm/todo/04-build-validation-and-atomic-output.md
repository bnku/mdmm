# Задача 04. Build-валидация и атомарный output

**Статус:** ⏳ Запланировано

## Цель

Сделать `build` главным publish-step для `mdmm`: он должен по умолчанию валидировать уже раскрытые Mermaid-диаграммы и не оставлять пользователю частично собранный output после первой же ошибки.

Задача должна убрать двусмысленность между `check` и отдельным validate-скриптом: `check` проверяет логику include/templating/resolution, а `build` дополнительно гарантирует, что итоговый Mermaid валиден для дальнейшей публикации.

## Источники требований

- `../00-roadmap.md`
- `../../src/cli.js`
- `../../src/preprocess.js`
- `../../scripts/validate-mermaid-cli.js`
- Пользовательский запрос в текущей DX-сессии: отдельный публичный `validate` не нужен; если валидация обязательна, она должна жить внутри `build`.

## Что входит в задачу

- Добавить встроенную Mermaid-валидацию в `mdmm build` по умолчанию.
- Добавить явный opt-out через `--no-validate`.
- Разделить maintainer-level example/e2e validation и user-facing build validation.
- Сделать directory build двухфазным: сначала staging и валидация, затем запись финального output.
- Переиспользовать один validation-слой и для CLI, и для repo smoke/e2e задач, чтобы не плодить две независимые реализации.

## Что НЕ делаем в этой задаче

- Не добавляем отдельную публичную команду `mdmm validate`.
- Не переводим `check` в тяжелую рендер-проверку.
- Не пытаемся в этой задаче делать автоисправление невалидного Mermaid.
- Не завязываем публичный `build` на `npx`-скачивание зависимостей в момент исполнения.

## Основные задачи по слоям

### Feature

- Встроить шаг Mermaid-валидации в путь `build` для single-file, stdout и directory mode.
- Зафиксировать разделение ролей: `check` быстрый и структурный, `build` - publish-oriented и строгий.
- Реализовать staging flow для directory build, чтобы падение на одном документе не оставляло часть файлов уже записанными в `outputDir`.
- Добавить CLI-флаг `--no-validate` для осознанного отключения финальной Mermaid-проверки.
- Выделить общий validator-модуль из текущего repo-скрипта и использовать его как библиотечный слой.

### Backend

- Отдельный backend не требуется.
- Если документация собирается в CI/CD, `build` должен оставаться детерминированным и не требовать сетевого доступа для валидации.

### Frontend

- UI продукта не затрагивается.
- Если docs frontend делает live preview только по исходному Markdown, README должен объяснять, что publish-гарантия наступает на `mdmm build`, а не в preview.

### Contracts/API

- Зафиксировать публичный контракт `mdmm build [input] [--output ...] [--no-validate]`.
- Зафиксировать, что отсутствие `--no-validate` означает обязательную проверку финальных Mermaid-блоков.
- Зафиксировать отдельный статус repo-скрипта `validate:examples`: это maintainer utility, а не пользовательская команда пакета.
- Если валидация падает, CLI должен сообщать источник ошибки на уровне файла и Mermaid-блока достаточно точно, чтобы автор мог локализовать проблему.

### Tests

- Добавить тесты, что `build` вызывает встроенную валидацию по умолчанию.
- Добавить тесты, что `build --no-validate` пропускает финальную Mermaid-проверку.
- Добавить тест на невалидный Mermaid: `check` проходит mdmm-level проверки, а `build` падает на финальной валидации.
- Добавить тесты на atomic directory build: при ошибке в одном файле финальный `outputDir` не содержит partial output.
- Добавить тест на single-file stdout mode, подтверждающий, что валидация выполняется и без записи в файл.

### Docs

- Переписать README-секцию про команды так, чтобы было ясно, почему `check` и `build` не дублируют друг друга.
- Явно объяснить судьбу текущего `validate-mermaid-cli.js`: он остается в репозитории как development/e2e инструмент, но не формирует основной пользовательский UX.
- Добавить короткую памятку: когда использовать быстрый `check`, а когда обязательный `build`.

## Критерии готовности

- `mdmm build` по умолчанию не выпускает невалидный Mermaid-output.
- Пользователь может явно отключить финальную валидацию через `--no-validate`, понимая последствия.
- При directory build нет partial output после ошибки в одном из документов.
- Пользовательская модель становится простой: `check` для быстрого прогона, `build` для публикационного результата.
