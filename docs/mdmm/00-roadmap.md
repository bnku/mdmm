# Roadmap: MDMM для Markdown-документации

## Назначение документа

Этот roadmap фиксирует согласованную последовательность внедрения синхронизации и переиспользования Mermaid-диаграмм в Markdown-документации без отказа от привычного authoring-подхода.

Документ является главным индексом feature-пакета `mdmm`.

## Источники требований

- Пользовательский запрос в текущей planning-сессии: сохранить `Markdown + Mermaid`, убрать копипасту и снизить риск неконсистентности.
- Исследование по архитектурным паттернам синхронизации Mermaid в экосистеме Markdown, предоставленное пользователем в текущей planning-сессии.
- `../01-intro-and-architecture.md`
- Пользовательский запрос в текущей DX-сессии: добавить onboarding, улучшить CLI output, упростить install/use cases и подготовить безопасный путь для будущего внедрения `mdmm` в уже существующие docs-проекты.

## Зафиксированные решения

- Основной путь внедрения: `MD-first preprocessor`, а не `DSL`, `JSON/YAML source model` или жесткая привязка к конкретному SSG.
- Канонические диаграммы и переиспользуемые фрагменты должны храниться в обычных `.md`-файлах, чтобы аналитики и бизнес продолжали работать в привычном формате.
- В первую очередь внедряется `include` целой диаграммы, потому что это самый простой и устойчивый способ снять основную боль от копипасты.
- Второй этап добавляет `include` фрагмента внутрь `mermaid`-блока только после стабилизации первого этапа.
- Синтаксис должен быть читаемым в исходном Markdown и не должен требовать от авторов знания внутреннего пайплайна сборки.
- Проверки консистентности и синтаксическая валидация Mermaid должны выполняться в CI.
- Публичный CLI должен одинаково хорошо работать в трех сценариях: локальный бинарь из репозитория, `npx mdmm`, глобальная установка `npm i -g mdmm`.
- Команда `mdmm` без явной подкоманды должна показывать help и короткие next steps, а не запускать скрытое действие по умолчанию.
- Для greenfield-проекта нужен отдельный интерактивный `mdmm init`, который создает минимально работоспособную структуру документации.
- Для существующих docs-проектов резервируется отдельная команда `mdmm adopt`; она не должна смешиваться с `init` и в первой версии должна оставаться безопасной и немутирующей.
- `check` остается быстрым структурным прогоном логики `mdmm`, а `build` становится основным publish-step и по умолчанию валидирует итоговые Mermaid-блоки.
- Публичная валидация внутри `build` должна быть bundled и offline-friendly; репозиторный `mermaid-cli`-скрипт может остаться только как maintainer-level smoke/e2e проверка.
- CLI должен иметь цветной, но отключаемый output; минимальная поддержка: `NO_COLOR` и `--no-color`.
- Любой directory build с валидацией должен быть двухфазным и не оставлять partial output, если один из файлов не прошел финальную проверку.

## Границы работ

### Что входит в первую очередь

- Спецификация минимального синтаксиса include для целых диаграмм.
- Препроцессор, который разворачивает include-блоки в обычный Markdown с Mermaid.
- Поддержка канонических блоков в `.md`-файлах с явными block id.
- Базовые проверки: путь, block id, циклы include, остаточные неразрешенные директивы.
- Валидация итоговых Mermaid-диаграмм в основном `build`-пайплайне и отдельная maintainer-level e2e проверка через `mermaid-cli`.
- Документация для авторов и правило работы с общей библиотекой диаграмм.
- Интерактивный onboarding для нового docs-проекта через `mdmm init`.
- Понятный command surface: `mdmm`, `mdmm --help`, `mdmm --version`, `mdmm build`, `mdmm check`, `mdmm report`.
- Встроенная Mermaid-валидация в `build` по умолчанию и явный opt-out через CLI-флаг.
- Цветной output CLI, который отделяет success, warning и error-сообщения.
- Документация по реальным сценариям использования: `npx`, global install и локальная установка как devDependency.

### Что переносится дальше

- Композиция нескольких переиспользуемых фрагментов внутри одной диаграммы.
- Alias/prefix rewriting для безопасной вставки фрагментов.
- Экспортируемые узлы (`exports`) и правила ссылок на них.
- Расширенные проверки конфликтов node id и ошибок связывания после раскрытия include.
- Генерация индекса usage-map или отчетов по неиспользуемым блокам.
- Полуавтоматическое внедрение `mdmm` в уже существующую документацию: поиск кандидатов на вынос в `shared`, отчет по дублирующимся диаграммам и безопасные рекомендации по миграции.
- Любая автоправка существующих документов, автоматический rewrite Mermaid-блоков и эвристический dedupe с записью на диск.

## Общие правила для всех task-документов

- Следовать схеме `feature -> tests -> docs`.
- Не вводить отдельный DSL или новую модель данных, пока задачу можно решить на уровне Markdown-препроцессинга.
- Не использовать include по диапазонам строк; только именованные блоки.
- Не разрешать неограниченную глубину вложенных include на первом проходе.
- Любые изменения синтаксиса должны сопровождаться примерами, негативными кейсами и правилами миграции документации.
- Любой build output должен проходить автоматическую Mermaid-валидацию до публикации.

## Порядок задач

### Задача 01. Include целых диаграмм

**Статус:** ✅ Реализован прототип

Цель: убрать массовую копипасту одинаковых диаграмм между Markdown-документами и ввести канонические Mermaid-блоки с безопасным и понятным include-синтаксисом.

Текущий результат: в `../../src/` реализован standalone CLI-препроцессор с командами `build` и `check`, добавлены примеры, unit-тесты и отдельный скрипт Mermaid-валидации через `mermaid-cli`.

Подробности: `./todo/01-whole-diagram-includes.md`

### Задача 02. Include фрагментов внутри Mermaid

**Статус:** ✅ Реализован прототип

Цель: добавить композицию больших диаграмм из переиспользуемых Mermaid-фрагментов без конфликтов node id и без ручной склейки текста авторами документации.

Текущий результат: в `../../src/` добавлена поддержка `type=fragment`, inline-директив `%% include: ... as ...`, alias-префиксации `<alias>__<node-id>`, проверки `exports`, примеры и автоматические тесты.

Подробности: `./todo/02-fragment-includes.md`

### Задача 03. CLI surface, init и базовый onboarding

**Статус:** ✅ Реализован прототип

Цель: сделать первый запуск `mdmm` понятным без чтения исходников, добавить greenfield-onboarding и зафиксировать устойчивый command surface для дальнейшего роста CLI.

Текущий результат: в `../../src/cli.js` реализован command-based CLI surface, добавлены `mdmm init`, `mdmm --version`, help + quick start без скрытого действия по умолчанию, non-interactive `init --yes`, starter scaffolding и placeholder-команда `mdmm adopt`.

Подробности: `./todo/03-cli-surface-and-init.md`

### Задача 04. Build-валидация и атомарный output

**Статус:** ✅ Реализован прототип

Цель: превратить `build` в надежный publish-step, который по умолчанию валидирует итоговые Mermaid-диаграммы и не оставляет partial output при ошибке.

Текущий результат: `build` теперь по умолчанию валидирует итоговый Mermaid через встроенный validator-модуль `../../src/validator.js`, поддерживает `--no-validate`, а directory build сначала собирает и валидирует все файлы и только потом пишет output без partial artifacts.

Подробности: `./todo/04-build-validation-and-atomic-output.md`

### Задача 05. Цветной output, help и user-facing документация

**Статус:** ✅ Реализован прототип

Цель: сделать CLI визуально понятным, а install/use cases - очевидными для пользователя, который впервые сталкивается с `mdmm`.

Текущий результат: добавлен `../../src/logger.js` с цветным success/error output и поддержкой `NO_COLOR` / `--no-color`, help переписан под реальные сценарии запуска, а `../../README.md` разделен на user-facing usage и maintainer/development workflows.

Подробности: `./todo/05-output-help-and-usage-docs.md`

### Задача 06. Placeholder для `adopt` и foundation для future retrofit

**Статус:** 🟡 Частично реализовано

Цель: зарезервировать безопасный путь для будущего внедрения `mdmm` в уже существующие docs-проекты и не смешивать этот сценарий с `init`.

Текущий результат: в CLI уже зарезервирована команда `mdmm adopt`, README/help явно разводят `init` и `adopt`, добавлены smoke/regression-тесты на placeholder-поведение. При этом реальный analysis/foundation слой для inventory, duplicate detection и migration suggestions еще не реализован.

Подробности: `./todo/06-adopt-placeholder-and-foundation.md`

## Ожидаемый итог

После завершения feature-пакета проект должен иметь:

- минимальный, понятный и документированный include-синтаксис поверх обычного `Markdown + Mermaid`;
- каноническую библиотеку переиспользуемых Mermaid-блоков в `.md`-файлах;
- сборочный шаг и CI-проверки, которые не дают опубликовать несинхронизированные или синтаксически невалидные диаграммы;
- поддержку двух уровней переиспользования: целой диаграммы и Mermaid-фрагмента;
- понятный CLI entrypoint для первого запуска, `npx`-использования и глобальной установки;
- `build`, который по умолчанию проверяет финальные Mermaid-блоки до записи результатов;
- документированный маршрут дальнейшего роста в сторону `mdmm adopt` для уже существующих docs-проектов.
